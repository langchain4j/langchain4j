# Tool Guardrails in Core ([#7065](https://github.com/langchain4j/langchain4j/issues/7065)) — Task Execution Plan

## Your Mission

Implement langchain4j issue [#7065](https://github.com/langchain4j/langchain4j/issues/7065): port the tool guardrail concept from quarkus-langchain4j into
`langchain4j-core` / `langchain4j`. This covers `ToolInputGuardrail`, which validates or rewrites tool
arguments before execution, and `ToolOutputGuardrail`, which validates or rewrites tool results before
the LLM sees them. Reuse the existing guardrail infrastructure (`Guardrail`, the request and result
types, `AbstractGuardrailExecutor`, exceptions, events and listeners). Apply the guardrails at the
single funnel point in `ToolService`, so local `@Tool` methods, programmatic tools, `ToolProvider`
tools and MCP tools behave identically on the sync, async and streaming paths.

The main motivation is **indirect prompt injection**: text returned by tools (fetched pages, search
snippets, MCP servers, exception messages echoing remote content) reaches the LLM unchecked today.

### Execution Order in `ToolService` (both sync and async)

1. `beforeToolExecution` callback (unchanged)
2. Hallucinated name → hallucination strategy and **skip guardrails** (D14)
3. Input guardrails → rewrite (arguments JSON) / non-fatal → error result, tool **not** executed / fatal → exception (D3, D4)
4. `executeWithErrorHandling[Async]` (unchanged; guardrails run **outside** it, so `ToolExecutionErrorHandler` never sees guardrail exceptions)
5. Output guardrails, **including on error results** (D5) → rewrite (contents / `isError`) / non-fatal → error result / fatal → exception
6. `afterToolExecution` callback, `ToolExecutedEvent`, `ToolExecution` and chat memory all see the **guarded** result,
   and, after an input rewrite, the **rewritten** request (D18)
7. Compensation bookkeeping compares the original and the guarded result (D11): original success → guarded error
   means "output rejected" (compensable with the original result, failed step)

### Documentation Must-Haves (collected from the discussion)

- A non-fatal failure message is sent to the LLM **verbatim**, so it is fully under the user's control.
- **Never quote the checked content in a failure message.** For example,
  `Blocked suspicious instruction: "<snippet>"` sends the injection to the LLM anyway (@PSchmitz-Valckenberg).
- **LLM-as-judge guardrails can be injected themselves.** Pass the tool result to the judge as data, or combine
  it with a non-LLM check (@PSchmitz-Valckenberg).
- **A rejected output usually comes back identical on retry** (same URL, same page). The LLM may call the tool
  again up to `maxToolCallingRoundTrips` (default 100) times, and each guardrail run may be a paid model call.
  Use `fatal(..)` in that case, or a failure message that tells the LLM not to retry (@dliubarskyi).
- **Output guardrails also see error results**; use `isError()` to opt out (D5).
- **Resolution order (D6):** every tool guardrail that applies runs, in the order builder → class → method /
  `AiServiceTool`. Call out prominently that this **differs from AI service guardrails** (builder replaces the
  annotations there). Show a guardrail that skips some tools via `toolName()` / `toolSource()` (no per-tool opt-out
  yet), and document the deduplication rule of D6: the same guardrail class from annotations or `*GuardrailClasses(..)` at several levels runs once, instances run once per distinct object, and a builder instance plus an annotation class naming the same class both run.
- Wrapping `ToolExecutor` / `McpToolProvider.toolWrapper(..)` is no longer needed for guardrails.
- Compensation behavior for rejected tools (D11). Next to `successWith(..)` for sanitizing, spell out **how far a
  `failure(..)` reaches**: every compensable tool of the **whole invocation** is rolled back, not only those of the
  current round, and with cross-agent compensation also the compensable tools that **other agents ran before**
  (@dliubarskyi). A rewrite with `isError == true` counts as a failure too.

### Compatibility Summary

For the PR body (task 14). Verified by the revapi runs above and by `grep` on 2026-11-18.

- **Source-compatible for normal use.** Revapi reports no break against 1.24.0 in any of the four modules.
- **May break exhaustive `switch`es in user code** over the extended sealed types (`GuardrailRequest`, `GuardrailResult`, `GuardrailResult.Failure`,
  `GuardrailException`, `GuardrailExecutorBuilderFactory`, `GuardrailExecutedListener`, and `GuardrailExecutor` / `AbstractGuardrailExecutor`'s builder
  hierarchy) and over `CompensationReason` (two new constants). Revapi does not model sealing. None exist in this repository: `grep` over every `.java` / `.kt` file
  for `case` labels naming these types or `CompensationReason` constants, and for `instanceof Input*/Output*` on them in main code, found none (a `switch`
  over a pattern on a variable of another name would not match; the build compiles, which is the real proof for this repository). Not checked for Quarkus
  or other downstream code.
- **No changes to** `@InputGuardrails`, `@OutputGuardrails`, `InputGuardrail` or `OutputGuardrail`.
- **Behavior is unchanged when no tool guardrails are configured:** no guardrail request is built and nothing extra is allocated (pinned by
  `ToolGuardrailServiceExecuteGuardrailsTest` and the unchanged AI service tests). Two behaviors of **MCP** do change (task 10; flag for @jmartisk):
  `list_resources` / `get_resource` are scoped to the clients of that `provideTools(..)` call. A null or blank `McpClient#key()` no longer fails
  `provideTools(..)` (review item 1, 2026-11-19): its tools get a `ToolSource.Mcp` with no server keys (`ToolSource.mcp(..)` now accepts an empty
  collection) and a WARN is logged once per client. See the task 10 outcome for all four.
- **Everything new is `@Experimental` (D19), except** `GenericGuardrailService` (+ its `Builder`), which the stable `GuardrailService` extends, and
  `ClassMetadataProviderFactory#resolveMethodKey` (user decision, 2026-11-17). Everything is `@since 1.25.0`.
- **Guardrail service hierarchy (task 06a):** `GenericGuardrailService` and its `Builder` are new and sealed; `GuardrailService` and
  `GuardrailService.Builder` became `non-sealed` and redeclare their methods for binary compatibility (removing a redeclaration fails revapi with
  `java.method.*TypeErasureChanged`, verified 2026-11-17); `AbstractGuardrailService` and `GuardrailService#aiServiceClass()` are deprecated since
  1.25.0; frameworks that subclass `AbstractGuardrailService` or implement `GuardrailService.Builder` (CDI, Micronaut) keep working.
- **Quarkus (#3162):** it needs no change for the sealed SPI factories (it provides none), uses `GuardrailService#executeGuardrails`
  (unchanged), and, **if it adopts tool guardrails, probably needs to override `resolveMethodKey`** in its `QuarkusClassMetadataProviderFactory`, whose keys are
  `AiServiceMethodCreateInfo`, not `Method`s (read from its source; not run).
