The guardrail system was built in a composable way so it can be extended and reused in other downstream frameworks (such as [Quarkus](https://quarkus.io) or [Spring Boot](https://spring.io/projects/spring-boot)). This section describes some of the extension points or "hooks" that are provided.

All of these extension points utilize the [Java Service Provider Interface (Java SPI)](https://www.baeldung.com/java-spi).

Those frameworks would provide an implementation.<br/> - It also creates the [tool guardrail](/tutorials/tool-guardrails) classes (from `@ToolInputGuardrails`/`@ToolOutputGuardrails` and the `toolInputGuardrailClasses(..)`/`toolOutputGuardrailClasses(..)` setters), so a DI framework needs no tool-specific code for that.<br/> - A Quarkus implementation may look something like [`CDIClassInstanceFactory`](https://github.com/langchain4j/langchain4j/blob/main/integration-tests/integration-tests-class-instance-loader/integration-tests-class-instance-loader-quarkus/src/main/java/com/example/CDIClassInstanceFactory.java)<br/> - A Spring implementation may look something like [`ApplicationContextClassInstanceFactory`](https://github.com/langchain4j/langchain4j/blob/main/integration-tests/integration-tests-class-instance-loader/integration-tests-class-instance-loader-spring/src/main/java/com/example/classes/ApplicationContextClassInstanceFactory.java) |

:::note
To customize guardrails, a framework provides a `ClassMetadataProviderFactory` and a `ClassInstanceFactory` and uses the default guardrail builders and services. It replaces the whole builder through `GuardrailServiceBuilderFactory` (or `ToolGuardrailServiceBuilderFactory`) only if it must.

A framework that runs its own tool loop can reuse the tool guardrails through `ToolGuardrailService`: it builds one with `ToolGuardrailService.builder(aiServiceClass)` (for the guardrails that apply to every tool), binds each tool with `bind(null, tool)`, passing the guardrails it found for the tool as the guardrails of the `AiServiceTool`, and runs each tool call with `executeGuardrails(key, request, requestParams, tool)`. The key that `bind(..)` returns carries the specification and the source of the tool, and only works with the service that returned it. A framework that builds the guardrail requests itself and calls `executeInputGuardrails(key, request)` / `executeOutputGuardrails(key, request)` (or their `Async` variants) builds them from the key: a request whose tool name, specification or source differs from the key's fails with an `IllegalArgumentException` (the `Async` variants fail their future), so a tool is never reported with another tool's specification or as less trusted than it is. A framework that builds its own `ToolServiceContext` for the tool loop of LangChain4j sets the service with `toolGuardrailService(..)` and the keys that `bind(..)` returned with `toolGuardrailKeys(..)`. A tool of the context without a key is bound on demand when it is called, so it gets at least the guardrails that apply to every tool.
:::
